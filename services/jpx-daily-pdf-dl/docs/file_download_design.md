# 書類本体ダウンロード処理の実装設計（2026-09-04）

日本取引所グループ（JPX）が公開する「株式相場表」日報PDF（`stq_YYYYMMDD.pdf`）を取得し、
生データのまま保存するサービスの設計。`finance-lake`レイク層モノレポ内の1サービス
（`services/jpx-daily-pdf-dl/`）として、`services/edinet-dl/`と並置する。

## 経緯・利用規約についての判断

- 東証の日々の株式相場表PDF（例:
  https://www.jpx.co.jp/markets/statistics-equities/daily/t13vrt000001v7aw-att/stq_20260901.pdf ）
  をCSV化する一回限りの作業を行った際、JPXサイトの利用規約
  （https://www.jpx.co.jp/term-of-use/）を確認したところ、以下の制約があることが分かった。
  - 著作権はJPXに帰属し、無断改変は禁止
  - 有償契約またはJPXの許可がない限り、**商用目的によるデータ収集及び二次利用はできない**
  - 生成AI等による学習・解析・生成利用について、権利侵害や「JPXが不利益を被る可能性のある
    一切の行為」を禁止する包括条項がある
  - EDINETのように「AI利用制限は無い」と明言されているわけではなく、グレーゾーンがある
- **本サービスは個人利用限定とし、配布・商用利用は行わない**。配布・商用利用の価値が
  出てきた場合は、JPXの有償データサービス（JPxData Portal等）への切り替えを検討する。
  無償の一次情報である当データは、あくまで個人の投資判断参考目的の範囲で使用する。
- 出典表記をリポジトリルートの`README.md`に記載する（詳細は後述）。

## 対象範囲

- **株式相場表（東証日報）関連のPDF/ZIPのみ**。他の統計情報（統計月報等）は対象外。
- 対象期間は**1981年1月〜現在**（1949年〜1980年分は対象外、2026-09-04決定）。
- 立会市場・ToSTNeT市場等、PDF内部の区分は問わず、PDF/ZIPファイルそのものを丸ごと生データ
  として保存する（中身の解釈・CSV化は後段の別リポジトリの責務。レイク層はファイルの取得・
  格納に特化する、というfinance-lake全体の方針に準拠）。

## 3つの独立した形式（実機確認済み、2026-09-04）

実機で複数の一覧・アーカイブページと実際のファイルを確認したところ、**同じ「株式相場表」
であっても、期間によって構造の異なる3つの形式が存在する**ことが分かった。しかも
これらは単純に時系列で切り替わる後継関係ではなく、**形式B・Cは直近13ヶ月程度で同じ日付を
重複してカバーする、独立した2つの公表物**である。

| 形式 | 対象期間 | 粒度 | 列構成・内容 |
|---|---|---|---|
| **A: レガシー日次** | 1981年1月〜2019年12月 | 日次（ZIP展開後） | 約定日／銘柄／銘柄略称／前場OHLC／後場OHLC／最終特別気配／売買高／うち立会外売買高／単位（Oracle BI Publisher生成） |
| **B: 月次簡易OHLC** | 2020年1月〜現在（進行中も含む） | 月次（1ファイル/月） | 約定年月日／銘柄コード／銘柄名称／前場OHLC／後場OHLCのみ（売買高等は無い、簡易版）。生成ソフトウェアは2022年12月→2023年1月でAntenna House→iTextに変わるが列構成は同一 |
| **C: 詳細日次** | 直近13ヶ月程度（ローリング） | 日次 | 市場区分・業種見出し、VWAP、最終気配、前日比、売買高、売買代金を含む最も詳細な版（`stq_YYYYMMDD.pdf`） |

**形式B・Cが重複する直近13ヶ月程度の期間は、両方を取得する**（2026-09-04決定。後段が
用途に応じて選べるようにするため）。

## サービス本体と使い捨てスクリプトの切り分け（2026-09-04決定）

形式A（1981〜2019年）は今後増えることも変わることも無い、完全に確定した過去データ。
形式Bの「確定済み過去年分」も同様に、月が1つ進んで新たに確定するだけで、既存分が
変わることは無い。この2つは`edinet-dl`の`migrate_zip_to_gz.py`と同じ位置づけの
**一回限りの使い捨てスクリプトで全件取得**し、以降はサービス本体のコードから完全に
切り離す（`--start-date`/`--end-date`のような汎用バックフィルCLIをサービス本体に
持たせない）。

サービス本体（systemdタイマーで動く定期実行ジョブ）が継続的に担うのは、以下の2つに
限定される。

- **形式C（詳細日次）**: 直近13ヶ月のローリングウィンドウを継続的に追いかける。
  `edinet-dl`と同様、日次実行＋数日分の遡り窓（`DAYS_WINDOW`相当）を持つ。
- **形式Bのうち`03.html`に現在列挙されている月**: `03.html`に現れている月を都度確認し、
  未取得なら取得する軽い処理（詳細は後述）。

## 取得方法（形式ごとに独立）

東証はEDINETのような「書類取得API」を持たない。形式ごとに取得方法が異なる。

### 形式A: レガシー日次（1981年1月〜2019年12月、パス直接指定、使い捨てスクリプト）

```
https://www.jpx.co.jp/markets/statistics-equities/daily/data/{yyyymm}.zip
```

`{yyyymm}`は年月から機械的に組み立てられるため、一覧ページを読まずに直接取得できる。
ZIPの中身は**1日1PDFがそのまま束ねられたもの**（例: `BO_C0076_20191202.pdf`）。展開して
個々の日次PDFとして保存する。

### 形式B: 月次簡易OHLC（2020年1月〜現在、期間により取得方法が変わる）

- **確定済み過去年分**（パス直接指定、スクレイピング不要、**使い捨てスクリプト**）:
  ```
  https://www.jpx.co.jp/markets/statistics-equities/daily/data/{yyyymm}.pdf
  ```
  `https://www.jpx.co.jp/markets/statistics-equities/daily/03/2011-2030.html`で
  パスパターンを特定済み。
- **確定アーカイブへの移行待ちの月**（一覧ページ解決が必要、不透明ID、**サービス本体**）:
  `https://www.jpx.co.jp/markets/statistics-equities/daily/03.html`から、
  `{yyyymm}.pdf`を含むリンク（例: `tvdivq0000001jan-att/202501.pdf`）を抽出して解決する。

**実機確認（2026-09-05）で判明した重要な訂正**: `03.html`は当初「当年進行中の月」と
想定していたが、実際は**確定済みアーカイブ（`data/{yyyymm}.pdf`）への移行がまだ済んで
いない月**を示すページだった。本稿執筆時点（2026年9月）で`03.html`には2025年1〜8月分
のみが列挙されており、2025年9月〜2026年分（現在進行中の期間）は一切現れない。つまり
JPXが確定アーカイブへ月次データを移行する作業には、実際にはかなりの遅延（1年以上）が
あると考えられる。

このため、サービス本体は固定の「当月」を仮定せず、**`03.html`に実際に列挙されている
月をそのまま対象にする**（列挙されている中で最新の月は確定前でまだ更新されうるため
毎回取得し直し、それより前の月は一度成功していればスキップする）。確定済みパスへの
直接アクセスによるフォールバック確認は、`03.html`に既に列挙されている月に対しては
不要（ページ自体が持つリンクをそのまま使えば良いため）。この確認は、確定アーカイブ
側にどこまで移行済みかを把握する必要がある**使い捨てバックフィルスクリプト側の関心事**
であり、サービス本体には持たせない。

### 形式C: 詳細日次（直近13ヶ月程度、一覧ページ解決が必要）

- 直近数日分: `https://www.jpx.co.jp/markets/statistics-equities/daily/index.html`
- 過去1年程度（月次アーカイブ）: `https://www.jpx.co.jp/markets/statistics-equities/daily/00-archives-{NN}.html`
  （`NN`は`01`〜`12`、`01`が直近の月、`12`が最も古い月）
- ページ内の`stq_YYYYMMDD.pdf`を含むリンクを正規表現等で抽出し、日付→実際のPDF URLの
  対応表を作る。

いずれの形式も、HTMLパースは一覧・アーカイブページに対してのみ行う（書類本体はURL指定で
直接取得するため、書類そのものへのスクレイピングは発生しない）。

## 保存先パス（形式ごとにトップレベルを分離）

```
data/raw/legacy-daily/{yyyy}/{mm}/{dd}/stq.pdf     ← 形式A（1981-2019、ZIP展開後）
data/raw/monthly-ohlc/{yyyy}/{mm}/stq_monthly.pdf   ← 形式B（2020-現在、月次のまま）
data/raw/detailed-daily/{yyyy}/{mm}/{dd}/stq.pdf    ← 形式C（直近13ヶ月、日次）
```

- **形式ごとにトップレベルディレクトリを分ける**（2026-09-04決定）。列構成・内容が
  形式間で全く異なるため、後段が同じ`{yyyy}/{mm}/`配下で「どの形式が存在するか」を
  ファイルの有無で判定する必要が無いようにする。パスを見ただけで形式が自明になる。
- `{yyyy}/{mm}/{dd}`の3階層は`edinet-dl`と揃える。形式B（月次のみ手に入る）は
  存在しない日次粒度を無理に作らないため`{yyyy}/{mm}`の2階層に留める（レイク層は
  生データを加工しない、という方針に従う）。
- 形式AのZIPは、`edinet-dl`のXBRL/CSV zip展開と同じ考え方で、**展開して中身の各日次PDFを
  個別に**保存する（zipのまま保存しない。DWH等での後利用を考慮し、後段が解凍ステップ
  無しに個々のファイルへアクセスできるようにするため）。
- ファイル名を`stq_{yyyymmdd}.pdf`ではなく`stq.pdf`とするのは、日付が既にディレクトリ
  階層に含まれているため冗長になるのを避けるため（`edinet-dl`の`document_list.json`と
  同じ考え方）。

## PDFの扱い

**生PDFのまま保存する。CSV変換・パースは行わない**（レイク層の責務外、後段の別リポジトリが
担う）。以前の一回限りの検証作業でCSV変換を試みた際、`pdftotext -layout`＋正規表現パーサーで
構造的に99.95%抽出できることを確認済みだが、その変換ロジック自体をレイク層に持ち込む必要は
無い。

## 冪等性・進捗管理

`edinet-dl`の`fetch_progress`とは別に、本サービス専用の進捗テーブルを新設する（DBファイルも
サービスごとに分離、`data/edinet-dl/`とは独立した`data/jpx-daily-pdf-dl/`配下に置く）。

形式B・Cが同じ日付を重複してカバーし、それぞれ独立に成功・失敗しうるため、主キーは
`period`単独ではなく**`(period, format)`の複合キー**とする。

```sql
CREATE TABLE fetch_progress (
    period TEXT,        -- 'YYYY-MM-DD'（形式C） or 'YYYY-MM'（形式A・B）
    format TEXT,         -- 'legacy-daily' | 'monthly-ohlc' | 'detailed-daily'
    status TEXT,         -- 'done' | 'error'
    sourceUrl TEXT,       -- 実際に取得したPDF/ZIPの完全なURL（出典表示・監査証跡用）
    message TEXT,
    fetchedAt TEXT,
    PRIMARY KEY (period, format)
)
```

**形式Aの粒度は日次ではなく月次とする**（2026-09-06修正。当初は形式C・日次バックフィルと
揃えて`YYYY-MM-DD`としていたが、バックフィル進捗レポート（後述）が年×月のマス目で表示
することに合わせ、形式A・Bとも`YYYY-MM`に統一した。形式AのZIPファイル自体が1ヶ月単位で
配布されており、ダウンロード・展開の成否も月単位でしか意味を持たないため、この変更に
実質的なデメリットは無い）。

- `sourceUrl`列は`edinet-dl`の`fetch_progress`には無い、本サービス固有の追加列。JPXのCMS
  コンテンツIDを含む不透明な実際のURL（形式Bの03.html列挙分・形式C）はダウンロード後に再現
  できないため、取得の都度記録しておく（利用規約上の出典表示、および後日「本当にこの
  URLから取得したものか」を追跡する監査証跡としての価値がある）。形式A・形式Bの確定済み
  過去年分（パス直接指定）はURL自体が`{yyyymm}`から再現可能だが、一貫性のため同様に記録する。
- `format`列により、形式B・Cが直近13ヶ月で重複しても、それぞれ独立に`done`/`error`を
  管理できる（例: 詳細日次(C)は失敗したが月次簡易(B)は成功、といった状態を別々に表現できる）。
- ファイル本体（`stq.pdf`／`stq_monthly.pdf`）の存在チェックによる冪等性は、`edinet-dl`の
  `save_atomic`パターン（一時ファイル→rename）をそのまま踏襲する。ZIP展開時は
  `extract_and_gzip`と同様、一時ディレクトリ→renameのアトミック性を踏襲する。

## リトライ・実行スケジュール

以下はサービス本体（形式C＋形式Bの03.html列挙分）にのみ適用する。形式A・形式Bの
確定済み過去年分は使い捨てスクリプトで一回限り取得するため、この節の対象外
（失敗時は手動で再実行すれば十分）。

- **リトライ設計**: `edinet-dl`と同じ2段階（実行内: 429・5xx・ネットワークエラーを最大5回
  指数バックオフ／実行間: 日付単位の進捗テーブル＋数日分の遡り窓）を踏襲する。
- **実行基盤**: 同じMac Mini上、systemdタイマーで実行する。`edinet-dl.timer`
  （`OnCalendar=*-*-* 04:01:30 Asia/Tokyo`）と電源投入〜シャットダウンの同じ時間枠
  （04:00〜06:00 JST）内に収める必要があるため、`jpx-daily-pdf-dl.timer`は
  `04:01:00 Asia/Tokyo`（edinet-dlより30秒早い）に設定した。`jpx-daily-pdf-dl.service`は
  マシンをシャットダウンしない。シャットダウンは全サービス共通の共有unit
  `finance-lake-shutdown.service`（リポジトリ直下の`systemd/`配下）が一手に引き受ける
  （2026-09-06決定。当初はedinet-dl.service側が最後に行う想定だったが、実行時間次第では
  それより前にshutdownが走ってしまう非対称な設計だったため、専用unitに分離した）。
  `finance-lake-shutdown.service`は`After=edinet-dl.service jpx-daily-pdf-dl.service`
  により、本サービスが実行中であればシャットダウンの開始を自動的に待つ。
- **HTTP接続**: `edinet-dl`が導入したKeep-Alive接続（`EdinetHttpClient`）は、1日あたり
  数百回のリクエストが発生する状況向けの最適化だった。本サービスは1日あたり月1回の一覧
  ページ取得＋1回のPDF取得程度で頻度が低く、Keep-Alive最適化の恩恵は薄いと判断し、
  `urllib.request`をそのまま使う素朴な実装で十分とする（over engineering回避）。

## Slack通知の設計（2026-09-06導入）

`edinet-dl`と同じ設計をそのまま踏襲する（「送られてきても見ない情報は送らない」方針、
1回のスクリプト実行につき1通のみ送信、新規環境変数`SLACK_WEBHOOK_URL`（任意、未設定
なら通知自体をスキップ）、`urllib.request`でのJSON POST、送信失敗は例外を上げずログに
記録するのみ）。

本サービスがedinet-dlと異なるのは、詳細日次・月次OHLC（簡易）という性質の異なる
2つの取得処理を1回の実行内で行う点。そのため、サマリは種別ごとに処理・成功・失敗
件数を分けて表示する。表示名は「詳細日次」「月次OHLC（簡易）」とし、設計ドキュメント上の
分類名（形式A/B/C）はそのまま出さない（2026-09-06修正。形式A/B/Cは本ドキュメント内の
便宜的な呼び名にすぎず、通知を見る側には意味を持たない内部実装の詳細が漏れていた）。

**成功時の例:**
```
✅ jpx-daily-pdf-dl 日次実行 成功
詳細日次: 処理3件 / 成功3件
月次OHLC（簡易）: 処理1件 / 成功1件
ダウンロード: 4件 / 5.2MB
リトライ発生: 0回
空き容量: 392.4GB
```

**失敗時の例:**
```
❌ jpx-daily-pdf-dl 日次実行 失敗 (1件)
詳細日次: 処理3件 / 成功2件 / 失敗1件
月次OHLC（簡易）: 処理1件 / 成功1件
失敗: 2026-09-05 (詳細日次) (ネットワークエラーが続くためリトライ上限に達しました)
ダウンロード: 3件 / 3.9MB
リトライ発生: 2回
空き容量: 392.4GB
```

edinet-dlの「429発生回数」は本サービスでは「リトライ発生回数」とした。edinet-dlは
一覧取得APIと書類取得APIで429を主要因として区別する意味があったが、本サービスは
リクエスト頻度が低く（1日あたり数回）、429・5xx・ネットワークエラーを合算して数えても
実用上十分なため、`_http_get()`内の単一のリトライ経路でまとめてカウントする。

送信タイミングは`main()`の最後（両形式の取得処理が終わった後、マシンのシャットダウン
＝共有unit`finance-lake-shutdown.service`が実行される前）。edinet-dlと同じくPythonアプリ
内で完結させる。

### 直近実行サマリの保存（`last_run_summary.txt`、2026-09-06追加）

Slackへ送信するメッセージ全文（改行保持）を、ログファイルと同じディレクトリに
`last_run_summary.txt`として上書き保存する（`save_atomic`を流用）。デプロイワーク
フローが、バックフィル進捗レポートの通知に併せてこの内容を転記するために追加した
（後述「CI（デプロイワークフロー）での自動生成」参照）。

既存のログ出力（`logger.info("summary: " + message.replace("\n", " / "))`）を再利用
しなかった理由: ログは改行を`" / "`に置換して1行に潰しているが、メッセージ本文
自体にも`" / "`が含まれる（例:「処理1件 / 成功1件」）ため、後から元の複数行構造を
一意に復元できない（実際にデプロイワークフロー側で復元を試みて、行が誤って分割
される不具合を実機で確認した）。ログ出力自体は人間が目視でログファイルを読む用途
としては十分なため変更せず、機械的に再利用する側のために別ファイルを用意する
という切り分けにした。

## バックフィル進捗レポート（2026-09-06導入）

形式A（1981-2019年）・形式B確定済み過去年分（2020年〜前月）のバックフィルは一回限りの
使い捨てスクリプト（未実装）が担うが、実装前の現時点でも「どこまで残っているか」を
把握できるよう、`scripts/backfill_report.py`を先に用意した。バックフィルスクリプト実行後の
状況把握だけでなく、実行前の「残作業一覧」としても機能する（未実施なら全マス空欄の
レポートが生成されるだけで、エラーにはならない）。

- **対象範囲**: 1981年1月〜（当月から既定20ヶ月遡った年月の前月）。当月直前の期間まで
  対象に含めてしまうと問題がある（2026-09-06修正）: 形式Cが直近13ヶ月程度をローリング
  ウィンドウで継続的に担当し、形式Bの確定アーカイブへの移行にも遅れがあるため、この
  期間はそもそも一回限りのバックフィルの対象ではなく常設サービスの担当。単純に
  「当月より前はすべて対象」としてしまうと、常設サービスの担当範囲が未実施の
  バックフィルであるかのように誤表示される。20ヶ月という値は、実機確認
  （2026-09-06、`data/{yyyymm}.pdf`への直接アクセス）で確定アーカイブが実際に
  2024年12月までしか無い（2025年1月分は404）と判明したことに基づく実測値（当初は
  「形式Cの13ヶ月ローリングウィンドウ＋1ヶ月の余裕」で14ヶ月と見積もっていたが、
  実際の遅れはそれより大きかった）。正確な確定境界はJPX側の移行状況次第で変動し
  今後もこのペースで進むとは限らないため、あくまで目安であり、`--end-year-month`で
  上書きできるようにした。この期間内の年（例: 当年）も、表からは消さずに全マス
  網掛けの行として表示する（常設サービスの担当範囲であることが一目で分かるように
  するため）。
- **表示形式**: 年（行、新しい年が上）×月（列）のコンパクトな表、1ヶ月1マス。
  バックフィル済みなら`*`、未実施なら空欄、対象範囲外は網掛け。画像等の装飾は使わず、
  罫線とベタ塗りのみで表現する。
- **データソース**: サービス本体と共有する`fetch_progress`テーブル（`DB_PATH`）を読むのみ
  （書き込みは行わない）。SQLite標準ライブラリのみで完結するため、Dockerを経由せずMac Mini
  ホストのPython3から直接DBファイルを指定して実行できる。
- **単一HTMLファイル**: 外部リソースへの依存無し。集計（完了ヶ月数・割合）はPython側で
  計算せず、生成されたHTML内の小さなJavaScriptがDOM上の`*`セルを数えて表示する
  （HTMLとロジックの二重管理を避けるため）。

### 常設サービス担当分（網掛け部分）の日次進捗表（2026-09-06追加）

月次の表で網掛けにした「対象範囲外」の期間は、一回限りのバックフィルの対象ではない
というだけで、常設サービス（形式C）が実際にどこまで取得できているかは別途気になる
（ユーザー指摘）。そのため、月次の表とは分離した日次の表を、ページの上部に別セクション
として用意した。

- **対象**: 形式C（詳細日次）のみ。形式Bの03.html列挙分は月次粒度のため、日次の表では
  意味を持たず対象外（月次の表と同じ粒度でしか確認できない）。
- **範囲**: 月次バックフィルの対象範囲外となる年月の1日から、前日
  （`last_complete_day_jst()`、サービス本体と同じ理由で当日は含めない）まで。月次の
  表の終端と日次の表の始端がちょうど接続し、抜け漏れなく全期間をどちらかの表で
  確認できる。
- **表示形式**: 年月（行、新しい方が上）×日（列、01〜31）。月に存在しない日（2月30日等）
  や前日より後の日は網掛けにする。集計・凡例の仕組みは月次の表と共通化する。

### CI（デプロイワークフロー）での自動生成（2026-09-06導入）

`jpx-daily-pdf-dl-deploy.yml`のデプロイ実行のたびに、Mac Mini上でレポートを生成し、
GitHub ActionsのArtifactとしてアップロードする。DBファイル自体はGitHub Actions側へ
転送しない（Mac Mini上でHTMLを生成してから、生成済みのHTMLだけを持ち帰る）。

- 既存のTailscale接続を再利用する（デプロイの`docker pull`と同じジョブ内）。
- リモートでのコマンド実行には既存の`appleboy/ssh-action`を使うが、ファイル転送
  （生成されたHTMLを持ち帰る）はこのactionではできないため、Ubuntuランナー標準搭載の
  素の`ssh`/`scp`を使う（新規の依存を増やさない）。
- `actions/upload-artifact`でアップロードする（既定の保持期間のまま、追加設定なし）。
- **Slack通知**（2026-09-06追加）: レポート生成のサマリ行、アップロードした
  Artifactへのリンク（`actions/upload-artifact`の`artifact-url`出力）、直近の
  日次実行サマリ（Mac Mini上の`last_run_summary.txt`をそのままSSH経由で読む）を
  1通にまとめてSlackへ通知する。GitHub Actions側に新規Secret`SLACK_WEBHOOK_URL`の
  登録が必要（Mac Mini上の`.env`とは別の場所。値は使い回してよい）。未設定でも
  通知がスキップされるだけでデプロイ自体は失敗しない（サービス本体の
  `send_slack_notification`と同じ設計）。ペイロードには`unfurl_links: false`・
  `unfurl_media: false`を指定する（有効のままだとArtifact URLの大きなプレビュー
  カードが表示され、テキスト部分が視覚的に埋もれてしまうことを実機で確認した）。
  Artifactのダウンロードには閲覧側もGitHubへのログインが必要（公開リポジトリでも
  匿名ダウンロードはGitHub側の制限で不可）。個人利用のため実害は無い。
- **実行タイミングについての留保**: デプロイは手動トリガー（`workflow_dispatch`）で
  コード変更時にしか実行されないため、レポートの更新頻度もそれに従う（アプリの
  デプロイ頻度とデータの進捗確認頻度は本来別の関心事）。バックフィル作業を追跡する
  用途で毎日確認したい場合は、スケジュール実行（`schedule`トリガー）の専用ワークフロー
  に分離することも検討の余地がある（未実施）。

## 確定済みアーカイブの一回限りバックフィルスクリプト（実装、2026-09-06）

`scripts/backfill_confirmed_archive.py`として実装（実機のJPXサイトに対して2019年
12月・2020年1月分で実データ取得を確認済み）。サービス本体（`fetch_jpx_daily.py`）と
DB・データディレクトリを共有する（`DB_PATH`・`DATA_DIR`は同じ環境変数）。

```
python3 scripts/backfill_confirmed_archive.py                 # 形式A・確定済み形式Bの両方
python3 scripts/backfill_confirmed_archive.py --legacy-only    # 形式Aのみ
python3 scripts/backfill_confirmed_archive.py --confirmed-only # 確定済み形式Bのみ
python3 scripts/backfill_confirmed_archive.py --force          # 既にdoneな月も再取得
```

- **形式A**（1981年1月〜2019年12月、468ヶ月）: `data/{yyyymm}.zip`を取得し、中身の
  日次PDF（例: `BO_C0076_20191202.pdf`）を個々に`legacy-daily/{yyyy}/{mm}/{dd}/stq.pdf`
  へ展開する。ファイル名の接頭辞は年代によって変わりうるため、末尾の8桁日付のみを
  正規表現で抽出する（実機確認: 1981年1月分93MB・2019年12月分17MB・21ファイル、
  いずれも想定通り取得できた）。
- **確定済み形式B**（2020年1月〜前月）: `data/{yyyymm}.pdf`を月ごとに取得し、
  `monthly-ohlc/{yyyy}/{mm}/stq_monthly.pdf`へ保存する。サービス本体が`03.html`
  経由で既に取得済みの月（後にJPXが確定アーカイブへ移行したもの）を上書きする形に
  なるが、内容は同じはずなので問題ない。
- **404の扱い**: JPXの確定アーカイブへの移行にはかなりの遅延（実機確認、2026-09-06:
  確定アーカイブは2024年12月分までで、それ以降は約20ヶ月の遅れ）があるため、直近の
  一定期間は`data/{yyyymm}.pdf`が404を返す。これは想定内の状態（「まだ確定していない
  だけ」）であり、`fetch_progress`にエラーとして記録せず黙ってスキップする（実機で
  2025年1月分の404を確認済み）。次回再実行時に再度チェックされるだけで、無限に404を
  吐き続けても実害は無い（このパスの確認自体が、
  JPX側の確定移行状況を把握する手段でもある）。
- **進捗管理**: サービス本体と同じ`fetch_progress`テーブルを共有する。粒度は
  月単位（`YYYY-MM`）で、`backfill_report.py`がそのまま読める（「冪等性・進捗管理」
  節参照）。
- **systemdタイマーには含めない**。手動実行のみ（`edinet-dl`の`migrate_zip_to_gz.py`
  と同じ位置づけ）。
- **未実施**: スクリプト自体は実装・実機確認済みだが、全件（468ヶ月＋確定済み形式B
  分）の実行はまだ行っていない。1981年〜2019年分は件数が多く、完了までかなりの
  時間がかかる見込み。

### ストレージ容量の見積もり（実測、2026-09-06）

複数時点にHEADリクエスト（ダウンロードは行わない）を送り、実測ベースで見積もった。

- **形式A**: 1999年3月→4月の境界でファイル生成方式が切り替わり、ファイルサイズが
  約90分の1に激減することが判明した（スキャン系→軽量な生成系への切り替えと推定）。
  単純な線形予測は使えないため、前後で別々にサンプリングしている。
  - 1981-01〜1999-03: 93.7MB〜173.8MB/月（やや右肩上がり）
  - 1999-04〜2019-12: 1.5MB〜17.4MB/月（緩やかに右肩上がり）
  - サンプル間を線形補間した合計: **約30.9GB**（468ヶ月）
- **確定済み形式B**: 2020-01〜2024-12（60ヶ月）、5.7MB〜7.6MB/月とほぼ一定。
  合計: **約0.4GB**
- **合計: 約31.3GB**。Mac Miniの空き容量430GB（`df -h /home`実機確認）に対して
  余裕は十分（使用率約7%）で、ストレージは問題にならない。
