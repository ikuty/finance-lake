# 書類本体ダウンロード処理の実装設計（2026-09-04）

日本取引所グループ（JPX）が公開する「株式相場表」日報PDF（`stq_YYYYMMDD.pdf`）を取得し、
生データのまま保存するサービスの設計。`finance-lake`レイク層モノレポ内の1サービス
（`services/jpx-daily-pdf-dl/`）として、`services/edinet-dl/`と並置する。

## 経緯・利用規約についての判断

- 東証の日々の株式相場表PDF（例:
  https://www.jpx.co.jp/markets/statistics-equities/daily/t13vrt000001v7aw-att/stq_20260901.pdf ）
  をCSV化する一回限りの作業を行った際、JPXサイトの利用規約
  （https://www.jpx.co.jp/term-of-use/）を確認したところ、以下の制約があることが分かった。
  - 著作権はJPXに帰属し、無断改変は禁止
  - 有償契約またはJPXの許可がない限り、**商用目的によるデータ収集及び二次利用はできない**
  - 生成AI等による学習・解析・生成利用について、権利侵害や「JPXが不利益を被る可能性のある
    一切の行為」を禁止する包括条項がある
  - EDINETのように「AI利用制限は無い」と明言されているわけではなく、グレーゾーンがある
- **本サービスは個人利用限定とし、配布・商用利用は行わない**。配布・商用利用の価値が
  出てきた場合は、JPXの有償データサービス（JPxData Portal等）への切り替えを検討する。
  無償の一次情報である当データは、あくまで個人の投資判断参考目的の範囲で使用する。
- 出典表記をリポジトリルートの`README.md`に記載する（詳細は後述）。

## 対象範囲

- **株式相場表（東証日報）関連のPDF/ZIPのみ**。他の統計情報（統計月報等）は対象外。
- 対象期間は**1981年1月〜現在**（1949年〜1980年分は対象外、2026-09-04決定）。
- 立会市場・ToSTNeT市場等、PDF内部の区分は問わず、PDF/ZIPファイルそのものを丸ごと生データ
  として保存する（中身の解釈・CSV化は後段の別リポジトリの責務。レイク層はファイルの取得・
  格納に特化する、というfinance-lake全体の方針に準拠）。

## 3つの独立した形式（実機確認済み、2026-09-04）

実機で複数の一覧・アーカイブページと実際のファイルを確認したところ、**同じ「株式相場表」
であっても、期間によって構造の異なる3つの形式が存在する**ことが分かった。しかも
これらは単純に時系列で切り替わる後継関係ではなく、**形式B・Cは直近13ヶ月程度で同じ日付を
重複してカバーする、独立した2つの公表物**である。

| 形式 | 対象期間 | 粒度 | 列構成・内容 |
|---|---|---|---|
| **A: レガシー日次** | 1981年1月〜2019年12月 | 日次（ZIP展開後） | 約定日／銘柄／銘柄略称／前場OHLC／後場OHLC／最終特別気配／売買高／うち立会外売買高／単位（Oracle BI Publisher生成） |
| **B: 月次簡易OHLC** | 2020年1月〜現在（進行中も含む） | 月次（1ファイル/月） | 約定年月日／銘柄コード／銘柄名称／前場OHLC／後場OHLCのみ（売買高等は無い、簡易版）。生成ソフトウェアは2022年12月→2023年1月でAntenna House→iTextに変わるが列構成は同一 |
| **C: 詳細日次** | 直近13ヶ月程度（ローリング） | 日次 | 市場区分・業種見出し、VWAP、最終気配、前日比、売買高、売買代金を含む最も詳細な版（`stq_YYYYMMDD.pdf`） |

**形式B・Cが重複する直近13ヶ月程度の期間は、両方を取得する**（2026-09-04決定。後段が
用途に応じて選べるようにするため）。

## 取得方法（形式ごとに独立）

東証はEDINETのような「書類取得API」を持たない。形式ごとに取得方法が異なる。

### 形式A: レガシー日次（1981年1月〜2019年12月、パス直接指定）

```
https://www.jpx.co.jp/markets/statistics-equities/daily/data/{yyyymm}.zip
```

`{yyyymm}`は年月から機械的に組み立てられるため、一覧ページを読まずに直接取得できる。
ZIPの中身は**1日1PDFがそのまま束ねられたもの**（例: `BO_C0076_20191202.pdf`）。展開して
個々の日次PDFとして保存する。

### 形式B: 月次簡易OHLC（2020年1月〜現在、期間により取得方法が変わる）

- **確定済み過去年分**（パス直接指定、スクレイピング不要）:
  ```
  https://www.jpx.co.jp/markets/statistics-equities/daily/data/{yyyymm}.pdf
  ```
  `https://www.jpx.co.jp/markets/statistics-equities/daily/03/2011-2030.html`で
  パスパターンを特定済み。
- **当年分（進行中）**（一覧ページ解決が必要、不透明ID）:
  `https://www.jpx.co.jp/markets/statistics-equities/daily/03.html`から、
  `stq`ではなく`{yyyymm}.pdf`を含むリンク（例:
  `tvdivq0000001jan-att/202501.pdf`）を抽出して解決する。
- **フォールバック順**: まず確定済み過去年分のパスへ直接アクセスし、404等で存在しなければ
  `03.html`から解決する（年が明けて確定すると、直接パスのアーカイブへ移動すると推測される
  ため）。

### 形式C: 詳細日次（直近13ヶ月程度、一覧ページ解決が必要）

- 直近数日分: `https://www.jpx.co.jp/markets/statistics-equities/daily/index.html`
- 過去1年程度（月次アーカイブ）: `https://www.jpx.co.jp/markets/statistics-equities/daily/00-archives-{NN}.html`
  （`NN`は`01`〜`12`、`01`が直近の月、`12`が最も古い月）
- ページ内の`stq_YYYYMMDD.pdf`を含むリンクを正規表現等で抽出し、日付→実際のPDF URLの
  対応表を作る。

いずれの形式も、HTMLパースは一覧・アーカイブページに対してのみ行う（書類本体はURL指定で
直接取得するため、書類そのものへのスクレイピングは発生しない）。

## 保存先パス（形式ごとにトップレベルを分離）

```
data/raw/legacy-daily/{yyyy}/{mm}/{dd}/stq.pdf     ← 形式A（1981-2019、ZIP展開後）
data/raw/monthly-ohlc/{yyyy}/{mm}/stq_monthly.pdf   ← 形式B（2020-現在、月次のまま）
data/raw/detailed-daily/{yyyy}/{mm}/{dd}/stq.pdf    ← 形式C（直近13ヶ月、日次）
```

- **形式ごとにトップレベルディレクトリを分ける**（2026-09-04決定）。列構成・内容が
  形式間で全く異なるため、後段が同じ`{yyyy}/{mm}/`配下で「どの形式が存在するか」を
  ファイルの有無で判定する必要が無いようにする。パスを見ただけで形式が自明になる。
- `{yyyy}/{mm}/{dd}`の3階層は`edinet-dl`と揃える。形式B（月次のみ手に入る）は
  存在しない日次粒度を無理に作らないため`{yyyy}/{mm}`の2階層に留める（レイク層は
  生データを加工しない、という方針に従う）。
- 形式AのZIPは、`edinet-dl`のXBRL/CSV zip展開と同じ考え方で、**展開して中身の各日次PDFを
  個別に**保存する（zipのまま保存しない。DWH等での後利用を考慮し、後段が解凍ステップ
  無しに個々のファイルへアクセスできるようにするため）。
- ファイル名を`stq_{yyyymmdd}.pdf`ではなく`stq.pdf`とするのは、日付が既にディレクトリ
  階層に含まれているため冗長になるのを避けるため（`edinet-dl`の`document_list.json`と
  同じ考え方）。

## PDFの扱い

**生PDFのまま保存する。CSV変換・パースは行わない**（レイク層の責務外、後段の別リポジトリが
担う）。以前の一回限りの検証作業でCSV変換を試みた際、`pdftotext -layout`＋正規表現パーサーで
構造的に99.95%抽出できることを確認済みだが、その変換ロジック自体をレイク層に持ち込む必要は
無い。

## 冪等性・進捗管理

`edinet-dl`の`fetch_progress`とは別に、本サービス専用の進捗テーブルを新設する（DBファイルも
サービスごとに分離、`data/edinet-dl/`とは独立した`data/jpx-daily-pdf-dl/`配下に置く）。

形式B・Cが同じ日付を重複してカバーし、それぞれ独立に成功・失敗しうるため、主キーは
`period`単独ではなく**`(period, format)`の複合キー**とする。

```sql
CREATE TABLE fetch_progress (
    period TEXT,        -- 'YYYY-MM-DD'（形式A・C） or 'YYYY-MM'（形式B）
    format TEXT,         -- 'legacy-daily' | 'monthly-ohlc' | 'detailed-daily'
    status TEXT,         -- 'done' | 'error'
    sourceUrl TEXT,       -- 実際に取得したPDF/ZIPの完全なURL（出典表示・監査証跡用）
    message TEXT,
    fetchedAt TEXT,
    PRIMARY KEY (period, format)
)
```

- `sourceUrl`列は`edinet-dl`の`fetch_progress`には無い、本サービス固有の追加列。JPXのCMS
  コンテンツIDを含む不透明な実際のURL（形式Bの当年分・形式C）はダウンロード後に再現
  できないため、取得の都度記録しておく（利用規約上の出典表示、および後日「本当にこの
  URLから取得したものか」を追跡する監査証跡としての価値がある）。形式A・形式Bの確定済み
  過去年分（パス直接指定）はURL自体が`{yyyymm}`から再現可能だが、一貫性のため同様に記録する。
- `format`列により、形式B・Cが直近13ヶ月で重複しても、それぞれ独立に`done`/`error`を
  管理できる（例: 詳細日次(C)は失敗したが月次簡易(B)は成功、といった状態を別々に表現できる）。
- ファイル本体（`stq.pdf`／`stq_monthly.pdf`）の存在チェックによる冪等性は、`edinet-dl`の
  `save_atomic`パターン（一時ファイル→rename）をそのまま踏襲する。ZIP展開時は
  `extract_and_gzip`と同様、一時ディレクトリ→renameのアトミック性を踏襲する。

## リトライ・実行スケジュール

- **リトライ設計**: `edinet-dl`と同じ2段階（実行内: 429・5xx・ネットワークエラーを最大5回
  指数バックオフ／実行間: 日付単位の進捗テーブル＋数日分の遡り窓）を踏襲する。
- **実行基盤**: 同じMac Mini上、systemdタイマーで実行する。`edinet-dl.timer`
  （`OnCalendar=*-*-* 04:01:30 Asia/Tokyo`）と電源投入〜シャットダウンの同じ時間枠
  （04:00〜06:00 JST）内に収める必要があるため、`jpx-daily-pdf-dl.timer`は時刻をずらして
  設定する（具体的な時刻は実装時に決定。1日1ファイルのみの軽量な処理のため、実行時間は
  短い見込み）。
- **HTTP接続**: `edinet-dl`が導入したKeep-Alive接続（`EdinetHttpClient`）は、1日あたり
  数百回のリクエストが発生する状況向けの最適化だった。本サービスは1日あたり月1回の一覧
  ページ取得＋1回のPDF取得程度で頻度が低く、Keep-Alive最適化の恩恵は薄いと判断し、
  `urllib.request`をそのまま使う素朴な実装で十分とする（over engineering回避）。

## 出典表記

リポジトリルートの`README.md`に、EDINETと同様の形式で1文追加する。

```
出典：日本取引所グループ 統計情報（株式関連）、
https://www.jpx.co.jp/markets/statistics-equities/daily/index.html
```

個別ファイルごとの実際の取得元URL（一覧の列挙）はREADME.mdには含めない（日数分だけ肥大化
するため）。進捗テーブルの`sourceUrl`列に構造化データとして保持する（前述）。

## テスト方針

`edinet-dl`と同じ方針（新規テスト用ライブラリを追加せず、`unittest.mock`＋`pytest`の
`tmp_path`/`monkeypatch`で書く）。一覧ページのHTMLパース処理は、実際に取得したHTMLの
断片をテスト用フィクスチャとして保持し、リンク抽出ロジックを検証する。
