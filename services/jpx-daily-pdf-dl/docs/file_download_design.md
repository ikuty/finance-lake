# 書類本体ダウンロード処理の実装設計（2026-09-04）

日本取引所グループ（JPX）が公開する「株式相場表」日報PDF（`stq_YYYYMMDD.pdf`）を取得し、
生データのまま保存するサービスの設計。`finance-lake`レイク層モノレポ内の1サービス
（`services/jpx-daily-pdf-dl/`）として、`services/edinet-dl/`と並置する。

## 経緯・利用規約についての判断

- 東証の日々の株式相場表PDF（例:
  https://www.jpx.co.jp/markets/statistics-equities/daily/t13vrt000001v7aw-att/stq_20260901.pdf ）
  をCSV化する一回限りの作業を行った際、JPXサイトの利用規約
  （https://www.jpx.co.jp/term-of-use/）を確認したところ、以下の制約があることが分かった。
  - 著作権はJPXに帰属し、無断改変は禁止
  - 有償契約またはJPXの許可がない限り、**商用目的によるデータ収集及び二次利用はできない**
  - 生成AI等による学習・解析・生成利用について、権利侵害や「JPXが不利益を被る可能性のある
    一切の行為」を禁止する包括条項がある
  - EDINETのように「AI利用制限は無い」と明言されているわけではなく、グレーゾーンがある
- **本サービスは個人利用限定とし、配布・商用利用は行わない**。配布・商用利用の価値が
  出てきた場合は、JPXの有償データサービス（JPxData Portal等）への切り替えを検討する。
  無償の一次情報である当データは、あくまで個人の投資判断参考目的の範囲で使用する。
- 出典表記をリポジトリルートの`README.md`に記載する（詳細は後述）。

## 対象範囲

- **株式相場表（東証日報）PDF/ZIPのみ**。他の統計情報（統計月報等）は対象外。
- 対象期間は**1981年1月〜現在**（1949年〜1980年分は対象外、2026-09-04決定）。
- 立会市場・ToSTNeT市場等、PDF内部の区分は問わず、PDF/ZIPファイルそのものを丸ごと生データ
  として保存する（中身の解釈・CSV化は後段の別リポジトリの責務。レイク層はファイルの取得・
  格納に特化する、というfinance-lake全体の方針に準拠）。

## 取得方法（3層構造、実機確認済み）

東証はEDINETのような「書類取得API」を持たない。ただし実機で複数の一覧ページを確認した
ところ、**期間によって取得方法が3層に分かれている**ことが分かった。

| 対象期間 | 取得方法 | 実際のパス |
|---|---|---|
| 直近13ヶ月程度（日次） | 一覧ページ解決が必要（不透明ID） | `index.html`＋`00-archives-01`〜`12`から解決 |
| 当年分（月次、進行中） | 一覧ページ解決が必要（不透明ID） | `03.html`から解決（例: `tvdivq0000001jan-att/{yyyymm}.pdf`） |
| **確定済み過去年分（月次、1981年1月〜）** | **パス直接指定で取得可能** | `data/{yyyymm}.pdf`（2020年1月〜）／`data/{yyyymm}.zip`（1981年1月〜2019年12月） |

### 直近・当年分（不透明ID、一覧ページの解決が必要）

- 直近数日分: `https://www.jpx.co.jp/markets/statistics-equities/daily/index.html`
- 過去1年程度（月次アーカイブ）: `https://www.jpx.co.jp/markets/statistics-equities/daily/00-archives-{NN}.html`
  （`NN`は`01`〜`12`、`01`が直近の月、`12`が最も古い月）
- 当年分の月次まとめ: `https://www.jpx.co.jp/markets/statistics-equities/daily/03.html`
- いずれもページ内の`stq_YYYYMMDD.pdf`・`{yyyymm}.pdf`を含むリンクを正規表現等で抽出し、
  日付→実際のURLの対応表を作る（HTMLパースはこれらの一覧ページに対してのみ行う。書類本体
  はURL指定で直接取得するため、書類そのものへのスクレイピングは発生しない）。

### 確定済み過去年分（パス直接指定、スクレイピング不要）

`https://www.jpx.co.jp/markets/statistics-equities/daily/03/{範囲}.html`
（`2011-2030`・`1981-2010`の2ページ。`1949-1980`は対象外のため使わない）から、
パスパターンを特定済み。

```
https://www.jpx.co.jp/markets/statistics-equities/daily/data/{yyyymm}.pdf   ← 2020年1月〜2024年12月
https://www.jpx.co.jp/markets/statistics-equities/daily/data/{yyyymm}.zip   ← 1981年1月〜2019年12月
```

`{yyyymm}`は年月から機械的に組み立てられるため、**一覧ページを一切読まずに直接取得できる**。
実機確認で以下を確認済み。

- ZIP形式（1981〜2019年）: 中身は**1日1PDFがそのまま束ねられたもの**（例:
  `BO_C0076_20191202.pdf`のような日付入りファイル名）。現行の`stq_YYYYMMDD.pdf`とは
  ファイル名規則が異なるが、同じ日報の過去分。
- PDF形式（2020〜2024年）: **月次でまとめられた1つのPDF**（2024年1月分は1212ページ）。
  単日分（413ページ）の3倍程度に収まっており、単純に日次PDFを束ねただけではなく、
  簡略化された月次集計フォーマットの可能性がある（中身の解釈はレイク層の範囲外のため、
  詳細調査はしない）。

**この境目（現在は2024年12月）は時間とともに後ろにずれていく**。当年分（`03.html`で
不透明IDのまま提供されている分）は、年が明けて確定すると、翌年以降にこの直接パスの
アーカイブへ移動すると推測される。日次実行のたびに`03.html`と過去年アーカイブの両方を
確認する必要は無く、**過去年アーカイブに存在するかどうかをまず確認し、無ければ`03.html`
から解決する、というフォールバック順**で実装するのが妥当。

## 保存先パス

ソース側の粒度（日次 or 月次）に合わせて2種類のパスを使い分ける。日次データが手に入る
場合（直近の個別日次PDF、およびZIP形式アーカイブを展開した場合）は`edinet-dl`と同じ
`{yyyy}/{mm}/{dd}`の3階層、月次PDFしか手に入らない場合（2020〜2024年のPDF形式アーカイブ）
は`{yyyy}/{mm}`の2階層に留める（存在しない日次粒度を無理に作らない。レイク層は生データを
加工しない、という方針に従う）。

```
data/raw/{yyyy}/{mm}/{dd}/stq.pdf       ← 日次データが手に入る場合（直近の個別日次PDF、
                                            またはZIPアーカイブを展開した場合）
data/raw/{yyyy}/{mm}/stq_monthly.pdf    ← 月次PDFしか手に入らない場合（2020〜2024年のアーカイブ）
```

ZIPアーカイブ（1981〜2019年）は、`edinet-dl`のXBRL/CSV zip展開と同じ考え方で、**展開して
中身の各日次PDFを個別に**上記の日次パスへ保存する（zipのまま保存しない。DWH等での後利用を
考慮し、後段が解凍ステップ無しに個々のファイルへアクセスできるようにするため）。

ファイル名を`stq_{yyyymmdd}.pdf`ではなく`stq.pdf`とするのは、日付が既にディレクトリ階層に
含まれているため冗長になるのを避けるため（`edinet-dl`の`document_list.json`と同じ考え方）。

## PDFの扱い

**生PDFのまま保存する。CSV変換・パースは行わない**（レイク層の責務外、後段の別リポジトリが
担う）。以前の一回限りの検証作業でCSV変換を試みた際、`pdftotext -layout`＋正規表現パーサーで
構造的に99.95%抽出できることを確認済みだが、その変換ロジック自体をレイク層に持ち込む必要は
無い。

## 冪等性・進捗管理

`edinet-dl`の`fetch_progress`とは別に、本サービス専用の進捗テーブルを新設する（DBファイルも
サービスごとに分離、`data/edinet-dl/`とは独立した`data/jpx-daily-pdf-dl/`配下に置く）。

日次データ・月次データが混在するため、主キーは`fileDate`（`YYYY-MM-DD`）ではなく
**`period`（`YYYY-MM-DD`または`YYYY-MM`）**とする。

```sql
CREATE TABLE fetch_progress (
    period TEXT PRIMARY KEY,  -- 'YYYY-MM-DD'（日次） or 'YYYY-MM'（月次のみの期間）
    granularity TEXT,          -- 'day' | 'month'
    status TEXT,               -- 'done' | 'error'
    sourceUrl TEXT,             -- 実際に取得したPDF/ZIPの完全なURL（出典表示・監査証跡用）
    message TEXT,
    fetchedAt TEXT
)
```

- `sourceUrl`列は`edinet-dl`の`fetch_progress`には無い、本サービス固有の追加列。JPXのCMS
  コンテンツIDを含む不透明な実際のURL（直近・当年分）はダウンロード後に再現できないため、
  取得の都度記録しておく（利用規約上の出典表示、および後日「本当にこのURLから取得した
  ものか」を追跡する監査証跡としての価値がある）。確定済み過去年分（パス直接指定）は
  URL自体が`{yyyymm}`から再現可能だが、一貫性のため同様に記録する。
- `granularity`列で、その期間が日次単位（個別日次PDFまたはZIP展開後）で管理されているか、
  月次単位（月次PDFのみで日次に分解できない）かを区別する。後段のingestが、この列を見て
  読み方（日ごとに読むか、月ごとに読むか）を判断できるようにするため。
- ファイル本体（`stq.pdf`／`stq_monthly.pdf`）の存在チェックによる冪等性は、`edinet-dl`の
  `save_atomic`パターン（一時ファイル→rename）をそのまま踏襲する。ZIP展開時は
  `extract_and_gzip`と同様、一時ディレクトリ→renameのアトミック性を踏襲する。

## リトライ・実行スケジュール

- **リトライ設計**: `edinet-dl`と同じ2段階（実行内: 429・5xx・ネットワークエラーを最大5回
  指数バックオフ／実行間: 日付単位の進捗テーブル＋数日分の遡り窓）を踏襲する。
- **実行基盤**: 同じMac Mini上、systemdタイマーで実行する。`edinet-dl.timer`
  （`OnCalendar=*-*-* 04:01:30 Asia/Tokyo`）と電源投入〜シャットダウンの同じ時間枠
  （04:00〜06:00 JST）内に収める必要があるため、`jpx-daily-pdf-dl.timer`は時刻をずらして
  設定する（具体的な時刻は実装時に決定。1日1ファイルのみの軽量な処理のため、実行時間は
  短い見込み）。
- **HTTP接続**: `edinet-dl`が導入したKeep-Alive接続（`EdinetHttpClient`）は、1日あたり
  数百回のリクエストが発生する状況向けの最適化だった。本サービスは1日あたり月1回の一覧
  ページ取得＋1回のPDF取得程度で頻度が低く、Keep-Alive最適化の恩恵は薄いと判断し、
  `urllib.request`をそのまま使う素朴な実装で十分とする（over engineering回避）。

## 出典表記

リポジトリルートの`README.md`に、EDINETと同様の形式で1文追加する。

```
出典：日本取引所グループ 統計情報（株式関連）、
https://www.jpx.co.jp/markets/statistics-equities/daily/index.html
```

個別ファイルごとの実際の取得元URL（一覧の列挙）はREADME.mdには含めない（日数分だけ肥大化
するため）。進捗テーブルの`sourceUrl`列に構造化データとして保持する（前述）。

## テスト方針

`edinet-dl`と同じ方針（新規テスト用ライブラリを追加せず、`unittest.mock`＋`pytest`の
`tmp_path`/`monkeypatch`で書く）。一覧ページのHTMLパース処理は、実際に取得したHTMLの
断片をテスト用フィクスチャとして保持し、リンク抽出ロジックを検証する。
