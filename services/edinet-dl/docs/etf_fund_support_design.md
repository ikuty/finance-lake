# 設計: ETF（上場投資信託）対応

## 背景

2026-10-13、ユーザーから「1476 iシェアーズ・コア　Ｊリート　ＥＴＦのようなETFはどう
記録されているか」と問われたのを契機に調査。edinet-dlの取得フィルタ（secCodeが設定
されている書類、またはREITのformCode）はETFの書類を一切対象にしておらず、ETFの
EDINET開示はレイクに一度も取得されていないことが判明した。

## 構造上の問題: REITと異なりformCode単体では判別できない

ETF（＝EDINET上の「国内投資信託受益証券」、`ordinance_code='030'`、`formCode`
`04A`/`07A`/`10A`）は、REIT同様に書類一覧APIの`secCode`が常に`null`になる
（運用会社側のメタデータは「提出者単位」であり、提出者＝運用会社1社が多数のファンドを
`fundCode`で管理する構造のため、1社のsecCodeという概念自体が成立しない）。

しかしREITと決定的に違う点がある。**REITは1 edinetCode＝1投資法人＝1証券**という
1対1構造なので、`formCode`（07B/10B）という粗い判別子だけで対象を絞り込めた。一方
投資信託は**1 edinetCode（運用会社）配下に多数のfundCode（個別ファンド）**が存在し、
大半は非上場（実機確認: 国内投資信託全体で87社・5,410 fundCode。うちJPX上場ETFは
417本のみ）。`formCode`はファンド種別の粗い分類（受益証券かどうか）を示すだけで、
個々のfundCodeが上場ETFか非上場ファンドかを一切区別しない。

## DEI証券コードタグも信頼できない（REITとの違い、重要）

REIT対応時の実機確認（`services/edinet-dl/CLAUDE.md`参照）では、XBRL本体のDEI項目
`jpdei_cor:SecurityCodeDEI`（＝「証券コード、DEI」）が、書類一覧APIのsecCodeとは独立に
正しい証券コードを保持していた。これを投資信託にも使えると当初想定したが、**実機で
運用会社ごとの大規模サンプリング（3,910 fundCode、1件ずつ最新の有報CSVを取得）を行った
結果、この想定は誤りだった**。

| 運用会社 | サンプル数 | DEI証券コード設定あり |
|---|---|---|
| 大和アセットマネジメント | 578 | 0件 (0%) |
| ブラックロック・ジャパン | 112 | 0件 (0%、1476含む全ETFが該当) |
| ニッセイアセットマネジメント | 219 | 0件 (0%) |
| 三井住友トラスト・アセットマネジメント | 281 | 4件 (1.4%) |
| 野村アセットマネジメント | 548 | 80件 (14.6%) |
| シンプレクス・アセット・マネジメント | 32 | 19件 (59.4%) |
| Global X Japan | 77 | 66件 (85.7%) |

上場・非上場を問わず、運用会社によってこのDEIタグを一貫して空（`－`、全角ダッシュ＝
NULL相当）のまま提出する慣行がある（提出者側のXBRL生成ソフトやテンプレートの方言と
推測、未検証）。結果として国内最大手かつ最も著名なETF（大和・ブラックロック・ニッセイ
運用分）がことごとく拾えず、この経路は採用できない。

一方、**ファンド名称DEIタグ（`jpdei_cor:FundNameInJapaneseDEI`＝「ファンド名称
（日本語表記）、DEI」）は運用会社に依らず100%取得できる**（3,897件中3,897件、実機確認）。

## 採用した方式: JPX公式ETF一覧とのファンド名称テキスト照合

1. JPXサイトの「ETF全銘柄一覧」PDF（`https://www.jpx.co.jp/equities/products/etfs/
   issues/`配下、2026-10-09時点417銘柄）を取得し、銘柄コード・名称・運用会社を抽出。
2. JPXの運用会社名（21社）をEDINETの`filerName`（87社）と突き合わせ、ETFを実際に
   運用している15社の`edinetCode`を特定（残り72社は非上場ファンドのみ運用、または
   突き合わせ対象外）。
3. その15社配下の全fundCode（3,910件）について、最新の有報（07A優先、無ければ10A・
   04A）CSVを1件ずつ軽量サンプル取得し、ファンド名称DEIタグを抽出。
4. JPXの銘柄名（PDFのレイアウト崩れに対応するため、対象指標列と名称列が結合した
   "name_blob"として扱う）に対し、EDINET側のファンド名称が**末尾一致**するものを
   最優先、無ければ部分一致＋最短一致でフォールバックするテキスト照合を行う
   （正規化: NFKC・全角半角統一・中点/空白除去）。
   - 為替ヘッジ有無違いの姉妹ファンド（例: 「ＥＴＦ」と「ＥＴＦ（為替ヘッジあり）」の
     ような部分文字列関係）は、単純な部分一致だと誤って同じ銘柄に吸着する不具合が
     あったため、末尾一致を優先する方式に修正済み。
   - 1件のJPXコードに複数のfundCodeが一致してしまう曖昧なケースは、どちらが正しいか
     機械的に確定できないため両方とも除外する（推測で片方を選ばない）。
5. 結果: **417本中332本（約80%）を確認**（曖昧2件除外後）。1476含むブラックロック系
   ETFもすべて確認できた。残り約85本は、PDFのテキスト抽出時の行折り返し（長い指標名が
   名称列と結合し照合に失敗）や、レバレッジ/インバース型ETN（JPXの別カテゴリ扱い）等。
   REITの「14件の恒久的404」と同じ位置づけの既知の残差として許容する
   （後日再調査の余地あり、未着手）。

確認済み332件は`seed/edinet_etf_fund_issuers.csv`（edinet_code, fund_code, sec_code,
fund_name, note）として確認済みリスト方式で管理する（ir-disclosure-dlの
`edinet_reit_issuers.csv`と同じパターン。formCodeのような構造的フィルタが使えないため、
この方式が唯一の選択肢）。

## 実装（edinet-dl、finance-lake側）

- `fetch_documents.py`: `is_etf_fund(edinet_code, fund_code, etf_fund_keys)`を追加。
  日次取得フィルタに`(edinetCode, fundCode)`がseed記載のETFかどうかの判定を追加
  （既存のsecCode/REIT判定に加える、OR条件）。`load_etf_fund_keys()`でseedを読み込む。
- `backfill_etf.py`: 確認済みETFの書類本体を遡及的にダウンロードするワンショット
  スクリプト（`backfill_reit.py`と同じ構造）。
- `docker/Dockerfile`: `seed/edinet_etf_fund_issuers.csv`をイメージに含める。
