# 書類本体ダウンロード処理の実装設計（2026-08-25）

書類一覧APIによる進捗記録に加えて、書類本体（XBRL/PDF/CSV）をダウンロードして`/home`配下の
HDDに保存する処理の設計。**本設計は実装済み**（`scripts/fetch_documents.py`、2026-08-27）。
ローカル環境で実際にEDINET APIを叩いた実行確認済み（対象222件・成功222件・失敗0件、
Slack通知の実チャンネルへの着信も確認済み）。

容量面の裏付けは[storage_capacity_estimate.md](./storage_capacity_estimate.md)を参照。

## 対象範囲

- **全上場企業が対象**（`secCode IS NOT NULL`）。当初検討していた「ウォッチリスト企業のみ」は、
  Mac Mini化によりストレージ容量に十分な余裕ができたため取りやめる。ウォッチリスト機能は不要。
- 取得する書類形式は **`type=1`(XBRL)・`type=2`(PDF)・`type=5`(CSV化XBRL)の3種類のみ**。
  `attachDocFlag`（添付書類）・`englishDocFlag`（英文書類）は対象外（ファンダメンタル分析用途の範囲外）。
- **当面はCSV・PDFのみを対象とし、XBRLは対象外とする**（2026-08-28決定）。理由は以下の通り。
  - ファンダメンタル分析の核心（財務諸表の数値項目）はCSVの個別要素（`jppfs_cor:*`・
    `jpcrp_cor:*`）でクリーンな構造化データとして取得できる（本プロジェクト初期の実データ
    調査で確認済み）
  - CSVで失われるのは`*TextBlock`要素（セグメント情報の内訳・大株主の状況・役員一覧等、
    表構造がHTML除去で数字連結になってしまう補足的な開示）のみ。これらが必要になった場合は
    XBRL（iXBRLのHTML）を解析するか、PDFを人が読むことで代替できる
  - XBRLは1書類あたり展開後10〜20個の個別ファイルに分かれ、書類取得APIの呼び出し回数・
    ファイル数の大半を占める（実測: 2026-08-28の1日分で999ファイル中998件がXBRL由来）。
    対象外にすることでAPI呼び出し回数・ディスク使用量を大きく削減できる
  - `--xbrl`/`--pdf`/`--csv`のCLIフラグで対象typeを選択できるようにしており（後方互換の
    デフォルトは全形式）、補足情報が必要になった段階で`--xbrl`を追加すればよい。実装は
    `compute_enabled_types()`・`download_doc_files()`の`enabled_types`引数を参照

## 保存先パス

```
data/raw/{yyyy}/{mm}/{dd}/{edinetCode}/pdf/{docID}.pdf                  ← PDF（単一ファイル）
data/raw/{yyyy}/{mm}/{dd}/{edinetCode}/xbrl/{docID}/（元のzip内パス）.gz ← XBRL（展開・個別gzip）
data/raw/{yyyy}/{mm}/{dd}/{edinetCode}/csv/{docID}/（ファイル名）.gz     ← CSV（展開・個別gzip、フラット化）
```

**type（xbrl/csv/pdf）を最上位、docIDをその下に置く**（2026-08-28決定）。当初は
`{docID}_{type}`という1階層にまとめていたが、後段でのtype単位の一括読み込み（DWHローダが
「このtypeのファイルだけ全部読む」という使い方をしやすくする）を優先し、type別ディレクトリ
に分けた。docID階層を挟むのは、同一企業・同一日に複数docIDがある場合に、展開後のファイル名
（`manifest_PublicDoc.xml`等、EDINET側の命名は書類種別ごとに同名になりやすい）が衝突するのを
防ぐため。

CSV（type=5）のzip内部は常に`XBRL_TO_CSV/`という単一のラッパーフォルダしか持たない
（実測: 1〜2ファイルすべてこの直下）ため、`extract_and_gzip()`の`strip_prefix`引数で
この接頭辞を常に除去してフラットな構造にしている（件数によらず常に除去。docIDごとに構造が
不揃いになるのを避けるため）。XBRL（type=1）は`XBRL/PublicDoc/`・`XBRL/AuditDoc/`という
意味のある階層を持つため除去しない。

CLAUDE.mdの「書類本体（実データ）の保存」の項に記載済み。日付を最上位にするのは後段の
日次ingestが対象日のディレクトリだけを見れば済むようにするため、`edinetCode`を次階層に
するのは人間がレイクを直接見て判別しやすくするため。

**日付を`{yyyy}/{mm}/{dd}`の3階層に分ける**（2026-09-02決定）。当初は`{fileDate}`
（`2026-08-13`のような単一のディレクトリ名）を最上位に置いていたが、1年で365個・10年で
3650個のディレクトリが`data/raw/`直下にフラットに並ぶことになり、人間が`ls`で一覧した際の
見通しが悪い。`yyyy/mm/dd`に分けても、後段の日次ingestが対象日のパスを`yyyy/mm/dd`から
機械的に組み立てられる点は変わらないため、「対象日のディレクトリだけを見れば済む」という
設計意図は損なわれない。`response/`配下の一覧APIレスポンスも同様に`response/{yyyy}/{mm}/
{dd}/document_list.json`とし、ファイル名から`fileDate`を除いた（ディレクトリ階層に
含まれるため冗長）。実装は`date_hierarchy_dir()`。

**zip展開・個別gzip圧縮の方針（2026-08-28決定）**: XBRL・CSVはEDINETからzip形式で返るが、
DWH等での後利用を考慮し、**zipのまま保存せず展開した上で中身の各ファイルを個別にgzip圧縮**
して保存する。DWHのローダが解凍ステップ無しに`.gz`を直接ストリーム読み込みできることを
優先した（zipやtar.gzのようなコンテナ形式のままだと、後段で個別ファイルを扱う前に必ず
展開ステップが必要になる）。PDFは元々zipではないため単一ファイルのまま保存する。

実装は`extract_and_gzip()`。一時ディレクトリに展開・圧縮してから`os.replace`でrenameする
ことで、中断・失敗時に不完全なディレクトリが残らないようにしている（`save_atomic`の
一時ファイル→rename方式と同じ考え方をディレクトリ単位に拡張したもの）。冪等性の判定も
ディレクトリの存在チェックに変わる（ディレクトリが存在する＝展開が完全に完了している、
という保証がrenameのアトミック性によって成り立つ）。

## 書類一覧APIレスポンスの保存（2026-08-31決定）

```
data/raw/response/{yyyy}/{mm}/{dd}/document_list.json ← 一覧APIの生レスポンス（1日1ファイル）
```

書類本体（PDF/CSV/XBRL）だけでは、`docTypeCode`・`filerName`・`secCode`・`submitDateTime`
といったメタデータが失われる。これらはファイルを開いて中身を解析すれば一部は復元できる
（DEIタグ等）が、そもそも一覧APIが1回の呼び出しで無料で返してくれる情報であり、わざわざ
本体側から再構築する理由が無い。

一覧APIのレスポンスをそのまま（`secCode`等で絞り込む前の全件を）加工せず保存することで、
後段がこれらのメタデータを得るのにEDINET APIへ再アクセスする必要が無くなる。CLAUDE.mdの
「変更のたびにEDINETへ再アクセスせず保存済みの生データに対してのみ再処理できることが
重要」という方針に、書類本体だけでは実は沿えていなかったギャップを埋めるもの。

- 保存先を書類本体（`{fileDate}/{edinetCode}/...`）と分けて`response/`配下にまとめたのは、
  「日付ごとに1個」という書類本体（企業ごとに複数）とは性質の異なるファイルであるため。
- `fetch_day()`の呼び出しは日次実行で1日1回のみ（一覧APIにページングは無く、1回の呼び出しで
  その日全体が返る）。保存されるファイル数も日次1個・10年で最大3,650個程度で、書類本体
  （月2,700件超）に比べて無視できる規模。
- `secCode`で絞り込む前の全件を保存するのは、当リポジトリ側の絞り込み判断に後段が
  縛られないようにするため。
- 同日内に実行し直した場合は最新の内容で上書きする（同日中に後から追加提出される書類が
  あるため、日付単位の冪等性チェック＝スキップは行わない）。
- 実装は`save_list_response()`（`save_atomic()`を再利用）。

## 全体フロー

```
対象日について:
  1. 書類一覧API(type=2)を呼ぶ
  2. secCode IS NOT NULL の書類だけ対象にする
  3. 対象docIDごとに:
     - xbrlFlag/pdfFlag/csvFlag を見て、有効なtype(1,2,5)をループ
     - 保存先パス（PDFはファイル、XBRL/CSVはディレクトリ）に既に存在すればスキップ
     - 存在しなければ書類取得APIを呼び、PDFは一時ファイル→rename、XBRL/CSVは展開・個別
       gzip圧縮した上で一時ディレクトリ→renameでアトミックに保存
     - 各API呼び出しの間はREQUEST_DELAYを空ける（一覧取得・書類取得すべて対象）
  4. 対象docID全件のファイルが揃っていれば fetch_progress を'done'に、
     1件でも失敗があれば'error'にする
```

## 冪等性・進捗管理の設計（2階層）

新規の進捗テーブルは作らず、日付単位の既存`fetch_progress`とディスク上のファイル実体の
2階層で管理する。

- **日付単位（`fetch_progress`テーブル、既存のまま）**: その日の処理を試みたかどうかを記録。
  対象docID全件のダウンロードが**すべて成功**したら`status='done'`、1件でも失敗したら
  `status='error'`。`done`の日付は次回スキップ、`error`の日付は自動的に再試行対象になる。
- **ファイル単位（DBを使わず、ディスク上の存在チェックのみ）**: 個々のファイル
  （`{docID}_{type}.{ext}`）ごとの進捗テーブルは作らない。ダウンロード前に存在チェックし、
  存在すればスキップ、なければダウンロードして保存する。

2つの組み合わせにより、ある日の一部docIDだけダウンロードに失敗した場合でも、次回のプレーン
再実行で「一覧を再取得 → 既存ファイルはスキップ → 失敗分だけ再ダウンロード → 全件揃ったら
done」という形で自然に部分再開できる。DBとファイル実体の内容が食い違う不整合が原理的に
起きない構造になっている。

`--force`は「`fetch_progress`が`done`でも対象日を再チェックする」の意味に限定する（既存
ファイルは引き続き存在チェックでスキップされ、無駄な再ダウンロードは発生しない）。個別
ファイルを強制的に上書きしたい場合は、該当ファイルを手動で削除してから再実行する。

## リトライ設計（2段階）

一時的な障害（ネットワーク瞬断・EDINET側の一時的な過負荷等）による失敗を、実行内リトライで
できるだけ自己解決し、それでも解決しない場合のみ日をまたいだリトライに委ねる。

### 1. 実行内リトライ（同一実行内、最大5回・指数バックオフ）

既存の`fetch_day`は`429`（レート制限）のみをリトライ対象にしている。これを一般化し、
一覧取得API・書類取得APIの両方で共通の「HTTPフェッチ+リトライ」関数を使う。

```
リトライ対象（最大5回、指数バックオフ）:
  - 429（レート制限）
  - ネットワークエラー・タイムアウト（一時的な障害）
  - 5xxサーバーエラー

即座に失敗とする（リトライしない）:
  - 404等の4xx（そのtypeの書類が実際に存在しない、フラグと実体の不整合等。再試行しても無駄）
```

### 2. 実行間リトライ（既存の`fetch_progress`＋広げた`--days`ウィンドウ）

実行内リトライを使い切ってもなお失敗したファイルがある場合、その日の`fetch_progress`は
`error`のまま残る。これを翌日以降の実行で拾うには、日次実行の対象範囲を**1日ではなく
数日分の遡り窓**にする必要がある（`--days 1`では「今日」しか見ないため、前日の失敗が
永久に再試行されない）。`--days 3`程度にすることで、直近数日分の`error`日が毎回自動的に
再チェックされ、既にダウンロード済みのファイルは存在チェックで即座にスキップされる。

一時的な障害は1で吸収され、EDINET側の長時間障害など根の深い失敗だけが2に回る、という
役割分担になる。

窓の日数は環境変数`DAYS_WINDOW`（既定3日）でパラメータ化し、`--days`未指定時のデフォルト
値として使う（`.env`を変更するだけで調整でき、Dockerイメージの再ビルドやsystemd unitの
編集は不要）。実装済み（`scripts/fetch_documents.py`、2026-08-25）。

### 「今日」のタイムゾーンずれ（2026-08-31修正）

日次実行後、当日分（フロントの日付）が`fetch_progress`に一度も記録されない、という
事象を発見した。

**原因**: `main()`が`datetime.date.today()`で「今日」を計算していたが、これはコンテナの
システムTZ（`python:3.12-slim`は`TZ`未設定＝UTC固定）に依存する。`edinet-dl.timer`は
JST 04:01:30に発火するが、これはUTCでは**前日**19:01:30にあたる。実行時点のUTC日付は
まだ前日のままなので、`DAYS_WINDOW`の対象期間（`today`〜`today - (DAYS_WINDOW-1)`）が
JSTで見た実際の「今日」より常に1日古くなっていた。

DAYS_WINDOWによる遡り窓のおかげで日付そのものが永久に欠落するわけではなく、翌日の実行時
にはUTC日付が1日進んでいるため遅れて処理される（＝収集が常に1日遅れるという定常的な
ラグとして現れる）。データ消失ではないが、後段が「当日の朝には前日分が揃っている」という
前提を持つ場合は無視できないズレだった。

**対策**: `today_jst()`を新設し、`datetime.datetime.now(JST)`（`JST = timezone(timedelta(
hours=9))`という固定オフセット）で「今日」を計算するよう変更。固定オフセットのため
`tzdata`パッケージの追加インストールは不要（stdlibのみで完結）。

### 対象期間の終端は「今日」ではなく前日（2026-09-03修正）

`today_jst()`導入後も、別の不具合が残っていた。実際にMac Miniで、Tapoの電源OFF
スケジュールが働かずOS自動起動が発生せず、日次ジョブが本来の04:01:30 JSTに走らなかった
日があった。手動で電源投入した後の`Persistent=true`によるcatch-up実行で確認したところ、
その日（実行日当日）の一覧APIが`一覧0件`を返し、そのまま`fetch_progress`に`done`として
確定記録されていた。

**原因**: 日次ジョブは営業開始前のJST 04:01:30に実行される。この時点では**その日の
書類はまだ1件も提出されていない**ため、`DAYS_WINDOW`の対象期間に「今日」を含めても
一覧APIは常に0件を返す。この0件が`done`としてそのまま確定記録されると、`already_done()`
により、当日の本当のデータ（その日の営業時間中に提出される分）が**翌日以降も自動的には
二度と取得されなくなる**。実際、2026-09-01・09-02は自動実行では取りこぼしたままになって
いたことが判明した（09-01は本セッションの動作確認作業で偶然`--force`により復旧済みだった
が、09-02は欠損したままだった）。

**対策**: `last_complete_day_jst()`（`today_jst() - 1日`）を新設し、`DAYS_WINDOW`・
`--start-date`without`--end-date`の両方でこれを終端のデフォルトとするよう変更。日次
ジョブが何時に実行されようと、対象は常に「前日以前」に限定され、「今日」の一覧APIが
0件のまま確定記録されることが無くなる。

**デプロイの隙間で09-03分が同じ症状に遭遇（2026-09-04発見・復旧）**: この修正のビルド・
デプロイが完了する直前（2026-09-02 23:42 UTC＝09-03 08:42 JST）に、旧ロジックのまま
日次ジョブが1回実行され、09-03を対象に含めて`一覧0件`のまま`done`確定してしまった
（修正の反映は同日23:59 UTC＝09-03 08:59 JST 完了、17分の差でこの1回だけ間に合わな
かった）。修正後の翌日実行（09-04 04:03 JST）では、09-03は既に`done`扱いのため
`already_done()`によりスキップされ、対象から漏れていた。`--force`で09-03単独を
再実行し復旧（対象84件・成功84件・失敗0件）。ロジック自体は正しく機能しているが、
**コード修正のデプロイと、修正前に走った実行のタイミングが競合すると、同種の問題が
1日分だけ発生しうる**という点は、今後同様の「日付境界に関わる修正」をデプロイする際の
教訓として残しておく。

### IPv4接続の強制（2026-08-28追加）

バックフィル実行中（2026-08-27・28）、`ネットワークエラーが続くためリトライ上限に達しました
(<urlopen error [Errno 101] Network is unreachable>)`という失敗を複数回observedした。

**調査結果**: 429ではなく、EDINET側のレート制限とは無関係。Mac MiniのIPv6デフォルトルートが
Router Advertisement経由（`proto ra`、約1時間ごとに更新される期限付きの経路）であり、次の
更新までの間隙で経路が一時的に消える瞬間があると推測される（`ENETUNREACH`はカーネルが
「経路が無い」と即座に返すエラーで、タイムアウトではないことから、遅延ではなく瞬断が
起きていることを示唆する）。エラー直後に確認すると毎回すぐに疎通が回復していた。

**対策**: `force_ipv4()`で`socket.getaddrinfo`をIPv4のみに限定し、IPv6経路を使わないように
した。`main()`の最初で呼ぶことで、一覧取得API・書類取得API・Slack通知のすべてのHTTP接続に
適用される。stdlibのみで完結する標準的な手法（新規依存は不要）。

これは対症療法であり、根本原因（ルーター側のRA更新間隔等）を修正するものではない。IPv4接続
にも将来同様の問題が起きる可能性はゼロではないが、既存のリトライ設計（本セクション）で
実害なく吸収できる、という位置づけは変わらない。

### REQUEST_DELAYの下限とAPI呼び出しの並列化見送り（2026-08-30）

`REQUEST_DELAY`を1.2秒から段階的に0.1秒まで引き下げ、実運用（8月分バックフィル含む）で
429を一度も観測していない。ここからさらに高速化する手段として並列化を検討したが、見送った。

**「ダウンロード自体が暗黙の間隔になっている」**: `download_doc_files`は
`fetch_document_file`（HTTP応答の受信）→`extract_and_gzip`/`save_atomic`（展開・gzip圧縮・
ディスク書き込み）→`time.sleep(delay)`の順に同期実行される。次のEDINET API呼び出しが
飛ぶまでの実際の間隔は「明示的なsleep（delay）」だけでなく「ダウンロード受信時間＋展開・
圧縮・書き込みの処理時間」を含む。実測（2026-08-19、42件/15.5秒、delay=0.1秒）から逆算
すると、1呼び出しあたり約0.1秒の「隠れた待機」が処理時間として既に存在している。つまり
`delay`をゼロに近づけても、実際のリクエスト間隔はゼロには収束しない。

**並列化を見送った理由**: ダウンロード後の処理（展開・gzip圧縮・ディスク書き込み）は
EDINET側への負荷を伴わないため並列化しても問題ないが、API呼び出し自体を並列化すると
EDINET側から見て瞬間的に複数リクエストが同時到達することになり、利用規約の「短時間の
大量アクセスは禁止」という制約の精神に反する。429の文言（「取得間隔を見直してください」）
も逐次アクセスの間隔を前提にしていると考えられる。数値上の上限が公開されていない以上、
これ以上の高速化を狙って実際に閾値を探る（意図的に負荷をかけて確認する）行為自体が
避けるべき方針（IPv4強制の節などと同様、公的機関のAPIに対しては安全側に倒す）と整合しない。
現状の逐次・低頻度アクセスを維持する。

### 検証: フラグと実体の不整合は実際に起きるか（2026-08-25）

設計段階で「`xbrlFlag`等のフラグが立っているのに、実際に`type=X`を取得すると失敗する」
という不整合を懸念していた（フラグ更新のタイムラグ・訂正/取り下げ等を想定）。これが実際に
起きるか、過去1年分の実データを使って検証した。

**方法**: 過去1年から日付に幅を持たせて9日分（通常日・半期報告書シーズン・有価証券報告書
シーズン・提出集中日を含む）を選び、`secCode`付き書類を各日最大40件（計360件）サンプリング。
フラグが立っている形式について実際に書類取得APIを呼び、HTTPステータスとファイル先頭バイト
（zip/pdfのマジックナンバー）を検証した。

**結果**: 938リクエスト中、フラグと実体の不整合（flag=1なのに404・破損等）は**0件**。
検出された異常は20件のタイムアウトエラーのみで、すべて2025-11-14（年間最大の提出集中日、
secCode付き1,621件）に集中していた。他の8日は異常0件。

**結論**: 懸念していた「フラグと実体の不整合」は、少なくとも今回のサンプルでは発生しな
かった。観測された唯一の異常（提出集中日のタイムアウト）は、上記1.の実行内リトライ
（ネットワークエラー・タイムアウトを対象に最大5回・指数バックオフ）で既にカバーされる
failure modeである。そのため、フラグ不整合専用の分岐処理（その書類だけスキップ／日全体を
`error`にする、の判断）は**設計に追加しない**。ピーク日ほど一時的な失敗率が上がる傾向が
ある、という点は実運用上の留意点として記録しておく。

## ログ出力の設計

最小構成ポリシーに沿い、新しい保存先（別ログ用DB・別ログファイル管理サービス等）は作らず、
既存の2つの仕組み（実行時の出力・`fetch_progress`テーブル）を強化するだけに留める。

### 保存先: Python標準の`logging`モジュール（ファイル出力・sqlite出力ではなく）

`logging.handlers.RotatingFileHandler`を使い、サイズ基準で自己ローテーションするログ
ファイルに出力する。stdlib範囲内で追加依存はない。

```python
LOG_PATH = os.environ.get("LOG_PATH", "/data/logs/edinet-dl.log")
LOG_MAX_BYTES = 5 * 1024 * 1024   # 5MB
LOG_BACKUP_COUNT = 5              # 最大5世代 ≒ 合計25MB程度

logger = logging.getLogger("edinet-dl")
logger.addHandler(RotatingFileHandler(LOG_PATH, maxBytes=LOG_MAX_BYTES, backupCount=LOG_BACKUP_COUNT))
logger.addHandler(logging.StreamHandler(sys.stderr))  # 手動実行時にターミナルにも出す
```

- 保存先は既存の`/data`ボリュームマウント配下（`/data/logs/`）を流用。新しいDockerボリューム
  は不要
- ローテーションのサイズ・世代数は環境変数化せず定数で固定（チューニングする必要性が薄い
  ため、環境変数の増殖を避ける）。`LOG_PATH`のみ`DB_PATH`/`DATA_DIR`と同じパターンで環境
  変数化する

**検討した他の方式と不採用の理由:**

| 方式 | 不採用の理由 |
|---|---|
| SQLite出力（新規ログテーブル） | 新テーブル・肥大化対策（削除ポリシー）が必要になり、「ファイル単位の進捗はDBを使わない」という既存方針とも逆行する |
| `print`+シェルリダイレクト（`>> cron.log`）+ OSの`logrotate` | ローテーションのタイミングをOS標準の`cron.daily`任せにできない（Mac Miniは電源投入時間が限られ、OS標準のタイミングでは確実に実行される保証がない）。crontabに`logrotate`呼び出しを直列させる案も検討したが、電源スケジュールとログ管理という無関係な関心事が結合してしまう（器用貧乏）ため撤回した。`logging`モジュールなら実行のたびにアプリ内で自己完結してローテーションするため、電源スケジュールと完全に分離できる |

これにより、スケジューラ側（systemd unit）の変更は不要（`logrotate`呼び出し追加案は撤回）。
万一`logging`設定より前でクラッシュする稀なケース（Dockerイメージが無い等）は、systemdの
標準動作（journald経由、`journalctl -u edinet-dl.service`で確認可能）に任せ、そのための
独自の仕組みは作らない。

### 頻度・詳細度・内容

| タイミング | 内容 |
|---|---|
| 実行開始時 | 対象期間、`--force`有無を1行 |
| 日付ごと | 対象日、一覧件数、secCode絞り込み後の件数を1行 |
| 日内の進捗（20件ごと、または30秒ごと、いずれか早い方） | 処理済みdocID数/対象数、その日ダウンロードしたファイル数を1行（2026-08-28追加、`PROGRESS_LOG_INTERVAL_DOCS`/`PROGRESS_LOG_INTERVAL_SECONDS`） |
| ファイル失敗時のみ | docID、edinetCode、type、エラー内容を1行（**成功は個別に出力せず件数のみ集計**） |
| 日付処理完了ごと | ダウンロード成功/失敗件数、所要時間を1行 |
| 実行終了時 | 総処理日数、総成功/失敗ファイル数を1行 |

全上場企業対象だと1日数百ファイル規模になり得るため、正常系は件数集計に留め、異常系
（失敗）だけ詳細を出すことでログの実用性を保つ。日内の進捗ログも、1件ごとではなく
間隔を空けて出すことで同じ考え方を保っている。バックフィル等、1日の処理に数分〜十数分
かかる場合に、`tail -f`だけで日をまたぐ進捗・日内の進捗の両方を追えるようにするための
追加（それまではディスク上のファイル数を手動で数える必要があった）。

### `fetch_progress.message`の強化（既存カラムの活用）

新しいカラムは追加せず、既存の`message`カラムに失敗の要約を記録する（例:
`"3/312 files failed (see /data/logs/edinet-dl.log)"`）。DB側で「その日は何件失敗したか」
を一目で確認でき、詳細はログファイルを見に行く、という役割分担にする。

## Slack通知の設計

処理成功時/失敗時にSlackへ報告する。「送られてきても見ない情報は送らない」という方針で、
気になる情報だけに絞る。1回のスクリプト実行につき1通のみ送信する（日ごとではなく、実行
全体のサマリ）。

### 通知内容

**成功時の例:**
```
✅ edinet-dl 日次実行 成功
期間: 2026-08-24 〜 2026-08-26 (3日処理)
ダウンロード: 711件 / 128.4MB
429発生: 2回
空き容量: 421.3GB
```

**失敗時の例:**
```
❌ edinet-dl 日次実行 失敗 (1/3日)
期間: 2026-08-24 〜 2026-08-26 (3日処理、うち1日失敗)
失敗: 2026-08-25 (EDINET APIエラー status=500 message=...)
ダウンロード: 480件 / 89.1MB (成功分のみ)
429発生: 5回
空き容量: 421.3GB
```

含める項目とその理由:
- **失敗時のエラー内容**: `fetch_progress.message`と同じ内容をそのまま転記。次にどう対応
  すべきか判断できる、最も重要な情報
- **処理した日数**（`DAYS_WINDOW`による遡り分を含む）: 単発の遅延か、電源投入されない日が
  続いているといった根深い問題かを見分けられる
- **429（レート制限）発生回数**: 実行内リトライで吸収され普段は気づかないが、頻発すれば
  EDINET側の制限強化やアクセスパターン見直しのサイン
- **ダウンロード件数・サイズ**: リソースが限られたマシンでの運用状況を把握する材料
- **空き容量**: 同上（`shutil.disk_usage()`で`DATA_DIR`から取得、stdlibのみ）

含めないと決めたもの:
- **実行時刻**: Slackの通知時刻自体が兼ねるため不要
- **成功したファイル1件ごとの詳細**: ログ設計と同じ考え方（正常系は件数集計のみ、異常系だけ
  詳細を出す）
- **個別の銘柄名（EDINETコード・企業名）**: 実データで検証した結果、閑散日でも80社超、
  提出集中日（決算期）は800社超のEDINETコードが1日でダウンロード対象になることが分かった
  （2026-08-27実測、9日サンプル: 82〜830社/日）。この規模では銘柄名の列挙はどの日でも
  読みやすさの点で非現実的なため、件数のみとし個別名は載せない
- **ウォッチリスト的な仕組み**（特定銘柄だけ名指しで報告する等）: 現時点では検討しない、
  見送り（過去に「ウォッチリスト機能は不要」と判断した経緯とも整合）

### 実装方針

- **新規環境変数`SLACK_WEBHOOK_URL`**（任意、未設定なら通知自体をスキップ）。Slack Incoming
  Webhookへ`urllib.request`でJSON POSTするだけで、追加のSDK等は不要（stdlib範囲内）
- 通知送信は`try/except`で包み、**失敗しても例外を上げずログに記録するだけ**（ジョブ全体の
  成否には影響させない）
- 送信タイミングは`run()`の最後（スクリプト終了直前、systemd unitの2行目`shutdown`が
  実行される前）。Pythonアプリ内で完結させる（別のExecStart行やcurlコマンドを増やさない）

### 必要な追加トラッキング（既存設計への追加）

- **429発生回数**: リトライ関数内でカウンタを持つ（リトライの仕組み自体は既存設計のまま、
  カウントを追加するだけ）
- **ダウンロードサイズ・件数**: 書類本体ダウンロード処理でファイルを保存する際に累積する

## 環境変数

新規に`DATA_DIR`（デフォルト`/data/raw`）・`LOG_PATH`（デフォルト`/data/logs/edinet-dl.log`）・
`SLACK_WEBHOOK_URL`（任意、未設定なら通知スキップ）を追加する。既存の`DB_PATH`（デフォルト
`/data/edinet_index.db`）は変更しない。いずれも既存の`/data`ボリュームマウント配下に同居

├── raw/                 ← 新設のDATA_DIR

## テスト方針

新しいテスト用ライブラリは追加しない。既存テスト（`tests/test_fetch_documents.py`）で
既に使っている`unittest.mock`＋`pytest`の`tmp_path`/`monkeypatch`の延長で書く。

- **HTTPモック**: `urlopen`を`unittest.mock.patch`で差し替える既存手法をそのまま使う
  （書類取得APIも同じ`urllib.request`経由のため）。
- **リトライ・バックオフ**: `monkeypatch.setattr(time, "sleep", lambda _seconds: None)`で
  実待機をスキップする既存手法をそのまま使う。`side_effect`にタイムアウト例外
  （`urllib.error.URLError`等）を複数回並べてから成功レスポンスを返す形で、429・
  ネットワークエラー・5xx・即時失敗の4xxそれぞれの分岐を個別にテストする。
- **アトミック書き込み（一時ファイル→rename）**: `pytest`の`tmp_path`フィクスチャで実際の
  ファイルシステム上にテスト用ディレクトリを作り、(1)正常系でターゲットパスに正しい内容の
  ファイルができること、(2)ダウンロード中に例外を起こすモックを使い、ターゲットパスに
  壊れたファイルが残らないこと、を検証する。

**検討したが不採用**: `requests`向けのモックライブラリ（`responses`/`requests-mock`等）は
このプロジェクトが意図的に`requests`ではなく`urllib.request`（stdlib）を使っているため
合わない。`vcrpy`（実APIレスポンスの録画・再生）や`pytest-httpserver`（ローカルHTTP
サーバーを立てる統合テスト）はより実物に近いテストができるが、いずれも新規依存が増え、
この規模のテストには過剰と判断した。`requirements-dev.txt`の変更は不要。

## バックアップに関する注意点

`/data`を丸ごとバックアップすれば、このリポジトリが生成する状態（DB・書類本体）は全て
カバーできる。ただし以下の点に注意する:

- `raw/`配下は一時ファイル/一時ディレクトリ→renameで書き込むため、いつバックアップを
  取っても壊れたファイルを拾うことはない。
- `edinet_index.db`は、日次ジョブが書き込み中に単純コピーすると不整合な状態を拾う可能性が
  ある。日次ジョブ完了後・OSシャットダウン前のタイミングでバックアップを取るか、SQLite
  組み込みのオンラインバックアップ（`sqlite3 edinet_index.db ".backup backup.db"`）を使う。
- `.env`（APIキー）やリポジトリ本体はgit管理・再構築可能なため、データバックアップの対象
  には含めなくてよい（`.env`は秘匿情報として別途保管が必要な場合がある）。
