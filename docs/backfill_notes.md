## 2026-08-28: Mac Mini実機でSlack通知が届いていなかった不具合

2026-08-28 04:00 JSTの自動サイクル（ダウンロード0件・エラー無しの正常終了）でSlack通知が
届いていないことが発覚。ログには送信失敗のエラーも出ておらず、一見正常に見えた。

**原因**: Mac Miniの`/home/ikuty/edinet-dl/.env`は、書類ダウンロード機能（Slack通知含む）
を実装する**前**の初期セットアップ時に作成したものだった。実装後、ローカルの`.env`/
`.env.local`には`SLACK_WEBHOOK_URL`を追加していたが、**Mac Mini側の`.env`への反映を
忘れていた**。`SLACK_WEBHOOK_URL`は未設定時に通知を静かにスキップする仕様（エラーにも
ならない）のため、ログだけでは気づけなかった。

**修正**: Mac Miniの`.env`に`SLACK_WEBHOOK_URL`を追加。強制再実行（`--force`、0件の日を
対象に軽量に）で実際にSlackへ届くことを確認済み。

**教訓**: 新しい環境変数をアプリに追加した際、`.env.example`だけでなく、既にデプロイ済みの
実機の`.env`にも反映されているか確認する必要がある。`deploy.yml`はDockerイメージの更新のみ
を行い、`.env`ファイル自体は同期しない（`docs/mac_mini_setup_runbook.md`で手動作成した
ファイルのため）。今後、新しい環境変数を追加した際は、実機の`.env`を`.env.example`と
突き合わせて確認するとよい。

## 2026-08-27: 2026-08-01〜2026-08-27の部分バックフィル（中断）

### 実行内容

Mac Mini上でデタッチモードで実行。

```
docker run --rm -d --name edinet-backfill --env-file .env \
  -v /home/ikuty/edinet-dl/data:/data edinet-dl:latest \
  --start-date 2026-08-01 --end-date 2026-08-27
```

`REQUEST_DELAY`を**1.2秒→0.5秒**に短縮した状態での実地検証を兼ねた（EDINET API仕様書に
数値でのレート制限記載が無いことを確認済み。詳細は本ドキュメント末尾参照）。

### `docker stop`による中断は安全

`docker stop edinet-backfill`でコンテナを停止。アトミック書き込み設計（一時ファイル→rename）
により、`.tmp`の残骸は0件だった（確認済み）。`fetch_progress`は2026-08-06以降の行が
存在しないため（`process_day`完了前に停止したため）、次回同じコマンドを再実行すれば
2026-08-06から自動的に再開される（2026-08-01〜05はスキップされる）。

### 発見: 断続的なネットワークエラー（未解決、継続監視）

2026-08-06の処理中（約36分間）に、同一エラーが4回発生した。

```
ネットワークエラーが続くためリトライ上限に達しました (<urlopen error [Errno 101] Network is unreachable>)
```

**調査結果**:
- `429`ではない。EDINET側のレート制限とは無関係
- 発生時点でも`curl`での接続確認は成功（IPv6経由、`2603:1061:14:187::1`）しており、
  持続的な断絶ではなさそう
- `ping`はIPv4/IPv6とも100%パケットロスだが、これはEDINET側（Azure Front Door）が
  ICMPをブロックしているためと考えられ、実際の疎通とは無関係
- IPv6のデフォルトルートはRouter Advertisement経由（`proto ra`）。Mac Miniは有線LAN接続
  （インターフェース名`enp1s0f0`、Wi-Fiではない）だが、それでも瞬間的なRA更新の間隙が
  原因の可能性があるが、**根本原因は未特定**
- 936個体（うち3回は同一docID `S100YUK4`への異なるtype、興味深い偏り）に対して4件と、
  発生率としては低い

**今後**: 2026-08-28、対症療法として`force_ipv4()`（IPv4接続の強制）を導入した。詳細は
[file_download_design.md](./file_download_design.md#ipv4接続の強制2026-08-28追加)参照。
根本原因（ルーター側のRA更新間隔等）は未修正のため、IPv4接続でも将来同様の問題が起きる
可能性は残るが、既存のリトライ設計（実行内5回リトライ→それでもダメなら該当日を`error`の
まま次回に持ち越し）で実害なく吸収できる、という位置づけ。

### 参考: EDINET API仕様書の429に関する記載（2026-08-27時点で確認）

「EDINET API仕様書 Version 2.9」（2026年6月更新）P.83の記載（原文）:

> 429 Too Many Requests　大量リクエスト　一定時間内に大量のリクエストを受信しました。
> 十分な時間を空けて再試行してください。また、取得間隔を見直してください。

具体的な数値基準（秒間何リクエストまで等）は仕様書のどこにも記載が無い。429の説明自体、
Version 2.8（2026年5月）で追加されたばかりの記載だった。`REQUEST_DELAY=1.2`秒は公式の
数値根拠ではなく自主的に設定した値であり、実測（本記録時点で合計2,300件超のリクエストで
429発生0件）を根拠に0.5秒へ短縮した。
